# 比較実験で分かったこと（2026-10-14）

詳しい設計と生の数字は [flow-rethink-2026-10.md](flow-rethink-2026-10.md) の §5.5〜5.7 にある。ここには、そこから読み取れることだけを書く。

## 一言で

現行フロー全体を通しても、隠したテストで測れる品質は最小構成と変わらなかった。かかった時間は約 7 倍、コストは約 11 倍だった。差が見えたのは、敵対的レビューが欠陥を 1 件止めた場面だけだった。それも隠したテストでは見えず、別にテストを書いて確かめた。

## やったこと

- 大規模 Python プロジェクトの過去の変更 5 件（小 2、中 2、大 1）を、コピーの上で再演した。
- 条件は 2 つ。
  - A: 現行フロー全体（spec → plan review → 承認 → orchestrate → commit）
  - B: 手順の記述を外した最小構成。指示は「完了前にテストを実行し、結果を示せ」だけ
- 各条件 2 回ずつ、計 20 回。採点は、実際の修正 commit のテストを隠しておき、あとから流す方式。

## 分かったこと

### 1. 隠したテストの結果は、20 回すべてで A と B が同じだった

どのケースでも、A と B は同じテストに通り、同じテストで落ちた。既存テストの退行は、どの回にも無かった。

ただし、これは「品質が同じ」の証拠としては弱い。隠したテストは、条件の間の差を 1 度も拾っていない。測定器の目が粗すぎて、差があっても見えていない可能性がある（3 を参照）。

### 2. 時間とコストの差は大きく、毎回同じ向きだった

| | A | B | B / A |
|---|---|---|---|
| 時間（20 回の合計） | 218 分 | 32 分 | 約 1/7 |
| コスト（定価換算） | $86.8 | $7.6 | 約 1/11 |
| 出力トークン（1 回あたり） | 9〜22 万 | 0.6〜2 万 | 約 1/10 |

規模（小・中・大）を変えても、この比はほとんど変わらなかった。A の時間には人間の承認時間を入れていない。実際の運用では、A の差はさらに開く。

### 3. 隠したテストの外に、実在する欠陥があった

A の 1 回目で、Codex の plan review が BLOCK を出した。指摘の内容は「混在レコードを取りこぼし補完が拾うと、生データの確定値が NULL で上書きされる」。確かめるテストを書き、5 つの実装に流した。

| 実装 | 確定値 |
|---|---|
| 実際の修正（人間が承認して commit 済み） | 消える |
| A 1 回目（Codex のレビューあり） | 消えない |
| A 2 回目（Codex なし） | 消える |
| B 1 回目、2 回目 | 消える |

分かることは 3 つある。

- 隠したテストは、実際の修正が持つ欠陥を検出できない。実際の修正を正解として採点している以上、それより良い実装を見分けられない。
- 人間の承認も、この欠陥を通した。
- 欠陥を止めたのは、フローの過程（spec、フェーズ分割、Cycle doc）ではなく、出口側の敵対的レビューだった。同じ A でも、Codex が使えなかった 2 回目は止められなかった。

この混在レコードが本番で実際に起きるかは、確かめていない。

### 4. AI は、指示が無くても効くテストを書いた

AI が足したテストを修正前のコードで流すと、両条件とも一定数が FAIL した。効いているテスト、という意味。修正前でも通る空振りのテストばかり、という状態はどちらの条件にも無かった。

| | 修正前のコードで FAIL した件数 | テストの量 |
|---|---|---|
| A | 6〜39 件 | 多い |
| B | 2〜22 件 | A の 1/2〜1/4 |

B には「テストを先に書け」という指示もゲートも無い。それでも B のテストは空振りにならなかった。

### 5. 現行フローは、頼んでいない変更を毎回 commit に入れた

codify-insight が自動で走り、過去の Cycle doc、STATUS.md、`.claude/rules` を書き換えて commit した。パイロットを含めて 9 回中 9 回。B では 0 回。タスクの範囲を越えた変更が、修正と同じ commit に入る。品質の議論とは別に、これは直すべき挙動。

### 6. 決定論的ゲートは headless でも動く

pre-red-gate は、A の 10 回中 9 回で実行の痕跡がある。パイロットで痕跡が無かったのは、入口（spec と plan）を飛ばしていたため。入口を構造で通せば、ゲートは効く。

## 分からなかったこと

- **過程に価値があるか**。隠したテストより細かい物差しが無いので、判定できない。「価値が無い」とは言えない。「隠したテストで見える価値は無い」と言える。
- **規模が大きいと差が出るか**。大のケースは 1 件だけ。
- **レビュー指摘のうち、正しさに関わるものの割合**。数えていない。
- **人間の承認の効果**。自動承認で代用した。
- **Codex ありの A を 2 回そろえた比較**。途中で Codex の利用上限に達し、A の 2 回目はすべて Codex なしになった。

## 測り方の教訓

- **隠したテストは、実際の修正の水準までしか測れない**。それより良い実装も悪い実装も、同じ点になる。次の実験では、レビューが出した指摘を、確かめるテストに変えて採点に加える。
- **task の書き方の誤りは、両条件に同じだけ効く**。受け入れ条件の境界を「〜より古い」と書いたら、全 4 回が境界ちょうどを含めた。比較は崩れないが、点数そのものは下がる。
- **入口はプロンプトでなく、構造で通す**。「フローに従え」と書いても、AI は spec を飛ばした（パイロット）。plan mode で起動し、同じセッションを resume する 2 段階にしたら通った。
- **実験は外部の利用枠を消費する**。Codex の上限は、実験の途中で条件を変えてしまった。次は、実験の前に枠を見積もる。

## dev-crew への示唆（候補であって、決定ではない）

| 方向 | 対象 | 根拠 |
|---|---|---|
| 緩める | spec〜plan〜フェーズ分割〜Cycle doc の過程 | 1、2。隠したテストで見える寄与が無く、コストは約 11 倍 |
| 残す、固める | 出口側の敵対的レビュー | 3。今回、欠陥を止めた唯一の部品 |
| 残す | テストを正解の基準として守る部分（修正前に FAIL する、テストを改竄しない） | 4。ただし今回は、指示が無くても AI が守った |
| 直す | codify-insight の自動実行 | 5。範囲を越えた変更を毎回 commit に入れる |

どれも、次の実験の結果を見てから決める。

## 次の実験

B に敵対的レビューを 1 回だけ足した条件（B + レビュー）を測る。§5 の「1 部品ずつ足し引きする」方式。

### 結果（2026-10-15、5 件 × 2 回 = 10 回）

詳細は [flow-rethink-2026-10.md](flow-rethink-2026-10.md) の §5.8。

| | A | B | C（B + レビュー 1 回） |
|---|---|---|---|
| 時間（10 回の合計） | 218 分 | 32 分 | 79 分 |
| Claude のコスト | $86.8 | $7.6 | $18.8（ほかに Codex 74 万トークン） |
| 隠れた欠陥を止めた回 | 2 回中 1 回 | 0 回 | 2 回中 2 回 |

- **欠陥は、レビュー 1 回で止まった。** 実装後の diff に 1 回かけただけで、2 回とも止めた。フローの過程は要らなかった。
- **指摘は、正しさ 9 件、頑健さ 7 件。** 保守性・範囲外・誤検知は 0 件。同じケースの 2 回は似た指摘を出した。指摘が無いときは、AI は何も変えなかった。
- **新しい問題: AI は指摘を全部受け入れ、範囲を広げて直す。** 16 件中 16 件を採用した。設計を変える、日次処理を止める仕組みを足す、全モデルの再学習を生む、といった対応が人間の判断なしに入った。指摘は正しいが、対応の規模は人間が決める大きさだった。隠したテストで C が B より低く出た 2 回は、どちらもこれが原因。
- **測り方の訂正:** 確認テストが内部の関数を直接呼んでいたため、別の経路で直した実装を誤って FAIL にした。入口だけを呼ぶ形に直して測り直した。確認テストは、実装の内部の経路に依存させない。

### C': レビュー役を Claude にしても止まった（中 2 × 2 回）

C の Codex だけを、実行できる新しい文脈の Claude に置き換えた。2 回とも同じ欠陥を止めた。現行フローで Claude 側のレビューが見逃したのは、モデルの違いより、頼み方（壊れる入力を探させる）と道具（実行して再現できる）の違いで説明できる。Claude のレビュー役は low の指摘も出し、それへの対応で範囲がさらに広がった。詳細は §5.9。

### 示唆の更新（候補）

| 方向 | 対象 | 根拠 |
|---|---|---|
| 残す、固める | 出口側の敵対的レビュー 1 回（正しさと頑健さに絞る） | 欠陥を止めた。指摘はすべて正しさか頑健さだった |
| 足す | 指摘への対応が範囲・設計・運用を変えるときに人間に戻す判断点 | AI は指摘を全件採用し、範囲を広げて直した |
| 緩める | spec〜plan〜フェーズ分割〜Cycle doc の過程 | C は A の約 1/3 の時間、約 1/5 のコストで、A と同じ欠陥を止めた |

- B + レビューが、3 の欠陥を止めるか。止めるなら、現行フローの価値の大半は、約 1/10 のコストで取り出せる。
- レビューの指摘を分類し、正しさに関わるものの割合を数える（H4）。
- レビューの指摘を確かめるテストに変え、採点に加える。隠したテストより細かい物差しを作る。
- Codex の利用枠に余裕がある時期に流す。

## 指摘の振り分け（2026-10-16、修正段階 12 回 + 追加 4 回）

詳細は [flow-rethink-2026-10.md](flow-rethink-2026-10.md) の §5.10。

- **振り分けを入れると、範囲を広げる修正は無くなった。** 実装で触っていないファイルを変えた回は 12 回中 3 回から 0 回になり、欠陥は 4 回とも止まった。隠したテストは良くなった 3 回、悪くなった 2 回、同じ 7 回で、全体では変わらない。
- **悪くなった 2 回は、「ほかの機能には影響しない」という修正役の思い込みから。** 共有の処理の既存の動きを壊したが、その動きを確かめるテストが無く、修正役は気付けなかった。
- **呼び出し元を調べ、テストの無い動きを固定してから直させると、2 ケース中 1 ケースで直った。** 直らなかったのは、テストはあるが、テストが確かめていない状態（データベースの表の有無）で壊れたケース。環境で変わる前提は、受け入れ条件で先に決める必要がある。
