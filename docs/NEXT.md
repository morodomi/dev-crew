## 1. ポートフォリオとしての性格【決定済み 2026-09-11】

**決定**: dev-crew は洗練された成果物ではなく、AI と格闘した記録と、そこから実現した安定運用・思想を示すもの。社長個人のエンジニアとしてのポートフォリオの一部として位置づける。**cycle doc は削らない。**

この repo は公開ポートフォリオ（営業・転職）として維持する方針。資産は cycle doc に残る「AI コーディングの苦悩」— 失敗ペア 307 件、BLOCK 記録 23 件、再実行記録 86 箇所、「再発」の記述 83 箇所 / 27 doc。7 ヶ月の継続がないと貯まらない種類の記録で、再現困難。

**問題は価値ではなく伝わり方。** tracked 72,591 行のうち cycle doc が約 37%。読者が最初に開いた doc が 800 行の process 記録なら、読まれるのは「深さ」ではなく「要約できていない」。

### 決定の内容

主張は「plugin を作った」ではなく「格闘の記録 + そこから実現した安定運用 + 思想」。
cycle doc が差別化要因そのものであり、削減対象ではない。

### 選択肢

- **A. tip のみで受容** — 履歴と編集履歴は残る
- **B. in-place 書き換え（filter-repo + 強制 push）** — GitHub は rewrite 後も旧 commit が PR ref / cached SHA から到達可能と明記。PR diff も広く壊れる。**issue の編集履歴は git では消せない**
- **C. 旧 repo を rename + private 化し、sanitize 済み履歴で新 `dev-crew` を公開** — 汚染された issue / PR ごと private 側へ隔離できる。fork 0 / watcher 0 / star 1 なので移行コストは実質ゼロ
- **D. 受容 + 予防契約のみ** — remediation ではない。A〜C のいずれにも必須の追加策

**現時点の見立て: C が最も強い公開境界。** 1 の決定（cycle doc を資産として全保存）により「履歴は全量を持っていく」が前提になったため、C を採る場合も sanitize 対象は固有名のみで、commit 履歴そのものは維持される。残る論点は「issue / PR を移すか」。

`filter-repo --replace-text` は commit の親子関係・日時・message・diff をすべて維持する（変わるのは SHA）。「sanitize = 失う」ではない。

### 注意

- 個人 Gmail は「消すべき」ではなく「意図して選ぶ」項目。転職・営業用途なら本人と紐づくこと自体が目的でもある
- 強制 push は `.claude/rules/git-safety.md` で禁止。C を採れば不要

**Codex に「釣り合っているか」を問い直した結果、作ったものが過剰と判定された。縮小する。**

| 優先 | 内容 |

**ADR を実装後に回さない。** 判断部分を実装後に書くと、出来上がった設計の追認になる。今回の cycle がまさにそれで、設計が 3 回変わった末に「こうなりました」という記録だけが残った。

**縮小の内訳**（2026-09-16 訂正済み）

初版は「私も論理を確認済み」と書いたが、**その確認が誤っていた**（manifest C の項を参照）。「過剰だ」という評価と、個々の機構を安全に削れるという証明は別である。以下は**削る候補と、削る場合に残る保証・受容する失敗**の対応表として読むこと。

| 機能 | 判断 | 理由 |
|---|---|---|
| admission 3 条件 | 残す | 元要求そのもの |
| snapshot 上で実行 | 残す | 実行中の tree 書き換え問題を直接解く |
| manifest A→B の照合 | 残す | コピーが一貫した一点を表すことの確認 |
| **manifest C** | **削る候補（要判断）** | **当初「A=B なら一貫した一点」と書いたのは誤り。** `compute_manifest` はファイルを順に読むため、A の計算中に編集が入れば **A 自体が混成の観測**になる。A==B が示すのは「snapshot は A が観測した混成と一致する」だけ。C を足しても原子的 snapshot にはならない。**どちらの案も保証は同じではなく、「どこまでの検出を要求するか」の選択である。**削る根拠は「保証が同じ」ではなく「検出範囲を狭める代わりに機構を減らす」。縮小時にこの前提で決め直す |
| **PID・起動時刻・owner・ABA 対策 reaper** | **削る** | ただし**代わりに age 単独削除を入れない**。13〜17 分は実測値であって上限ではなく、停止・ハング・スリープ中の実行を消し得る。**通常終了の掃除は残し、強制終了後の残骸は自動削除せず「回収対象」として報告する**。残骸を許容するほうが、削除の安全性を証明するより安い |
| TERM / INT / HUP trap と子の停止 | 残す | 通常の中断で即掃除する価値は高い |
| **JSON 設定の型検査** | **削る** | 閾値は定数でよい。調整要求が実際に出てから設定化する |
| **exit code 0〜5** | **縮小** | `0`=pass / `1`=test fail / `2`=有効な結果なし。引数誤りを分けるなら 3 まで |
| **live tree 変更の advisory** | **削る** | snapshot を採った後はノイズ |
| **test 用 hook・source-as-library** | **削る** | テスト容易性のために production の状態空間を増やしている |

「kill 耐性」の定義も下げる。**「絶対に残骸を残さない」ではなく「通常終了では確実に消え、強制終了の残骸は可視化される」**。自動削除で解こうとしない。

### 複雑さ予算（`skills/spec` と `skills/review` へ）

行数ではなく**持ち込む状態の種類**を数える。行数だけを絶対化すると、AI は行を圧縮して読めない shell を作る。

数える対象: 永続状態・metadata / lifecycle・cleanup protocol / 設定形式・exit code・再試行状態 / OS 固有の process・filesystem 意味論への依存 / 並行性・所有権・時刻。

- **spec**: 「今回許す予算」を計画で宣言する（例: snapshot 1 / exit class 3 / 設定ファイルなし / 並行 protocol なし）
- **review**: **規模・保証・責務が増える指摘に限り** 3 択を出す — **(1) 今回直す (2) 削る・単純化して直す (3) リスクを明記して受容する**。あわせて「放置時の発現条件・影響・実測根拠」を 1 行。**明白な局所バグは AI がそのまま直す**（全 finding に三案を課すと、ceremony 自体が新たな肥大になる）
- 行数は拒否条件ではなく**警報**。超えたら自動 BLOCK ではなく Change Card と規模判断を必須にする
- 予算超過時の人間への確認は **cycle ごとに 1 回を目標**とする（今回の 9 回を再来させないため）。ただし**上限ではない**。再承認後にさらに境界を超えたら、回数を理由に黙って進めない。**まず AI が承認範囲へ縮め、無理なら止めて報告する**

### Change Card（cycle ごとに 1 枚、40〜60 行）

cycle doc は AI の監査証跡として正しいので削らない。**ただし入口にしない。** 人間の入口は Change Card。

書く内容: 何を変えるか / 変えないか・全体図のどの部品を触るか・採った案と捨てた案・複雑さ予算・意図して受容したリスク・完了時の実績差分と未解決事項。

`docs/OVERVIEW.md` が安定した地図、Change Card が「今回の地図上の赤丸」。構造が変わるときだけ OVERVIEW を更新する。

### 本 cycle で分かったこと（次に効く）

- **規律違反は本 cycle 中にさらに 2 件追加され計 6 件**。5 件目は sync-plan が admission なしでフルスイートを誤起動、**6 件目は PdM 自身**が worker 稼働中に並行してテストを起動した。「自分は分かっているから大丈夫」は成立しない
