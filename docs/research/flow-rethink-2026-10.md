# フロー再設計の思考メモ（2026-10）

作成: 2026-10-14 / 更新: 2026-10-14（Anthropic 公式情報の調査を §7 に追加し、§2・§4・§5 に反映）
位置づけ: 決定ではない。ADR を起こす前の材料。CONSTITUTION §1-2（思想）は引き継ぎ、Layer 3-4（手順）を見直す前提で書く。

## 0. 出発点

- 2026 年の Opus 5.5 / Fable 5.1 以降、TDD 中心で固めた手順が AI 駆動の開発に合っているか疑問が出た。正しくはできる。ただ 1 サイクルが長く、人間のレビューが 2 回（spec 前と完了後）挟まり、その人間のレビュー自体も長い。
- 「既存ルールに実害の記録がない」は、ルールを残す根拠にならない。ルールの内側では、ルールが無かった場合の効率を観測できない。
- 他組織の開発責任者と話して出た観察（固有情報は除いて一般化）:
  - 考慮漏れによる不具合は減った。残っている不具合は見つけにくい種類（性能、ドメインの正しさ）。
  - 性能の問題は、コードレビューではなく本番のアラートで見つかっている。AI が書き、人間がレビュー済みのコードで起きた。
  - AI を多用するチームほど、人間には読み切れない量の文章（AI スロップ）がやり取りされている。当事者は AI に要約させて読んでいるので困っていない。外から読む人だけが困っている。
  - 運用には幅がある。ゴールを渡すだけで済む領域もあれば、決済・認証のように人間の議論と診断を足す領域もある。ただし思想は揃えたい。
  - ゴールを 1 回渡すだけだと考慮漏れが出る。AI に質問させると延々と続き、上限を決めると文脈が足りない。

## 1. 思想（変えない）

- 人間が楽をするための開発体制
- 人間の判断負荷を減らしつつ、壊れにくい変更を高速に出す

前提（§3）のうち、次の 2 点は書き換えの候補になる。

| 旧 | 新 |
|---|---|
| AI は 90% 正しく、残り 10% を手順で埋める | 正しさは上がった。ただし失敗が消えたわけではなく、見つけにくい場所（文脈のズレ、非機能、ドメイン）に移った |
| ボトルネックはコードの正しさ | ボトルネックは人間と AI の間で情報をやり取りする部分。人間から AI へ意図を渡すことと、AI の出力を人間が理解することの 2 方向がある |

## 2. 論点ごとの検討

### 2.1 ズレは 2 方向で起きる

| 方向 | 起きること | 既存の部品 |
|---|---|---|
| 人間 → AI | 背景の文脈が渡らず、考慮漏れになる | spec、AskUserQuestion |
| AI → 人間 | 出力が長すぎて人間が理解できず、判断が遅れるか、形だけの承認になる | yomiyasu、explainer、first-reader |

- 良い点: yomiyasu と explainer は AI → 人間 側のための部品。すでにある。
- 弱い点: どちらも書いた後に直す道具で、生成を減らす道具ではない。explainer は資料を増やす方向にも働くので、使い方を誤るとスロップが増える。
- 案: 判断のための文書には、書く前に長さの予算を決める（2.3 の型）。yomiyasu と first-reader は、予算に収まったものを通す最後の検査として使う。
- 人間 → AI 側の「質問が延々と続く問題」への案: 間違えると高くつく点だけを質問し、残りは仮定を置いて進める。置いた仮定は一覧にして、完了時に人間へ見せる。人間は事前に全部答える代わりに、事後に仮定の一覧だけを確認する。

### 2.2 入口: spec を lint で検査するか

- 良い点: 決定論的で、漏れを最も安い段階で止められる。「過程は緩め、出口は固める」と組み合わせると、入口と出口を固めて間は任せる形になる。
- 弱い点: lint が見られるのは形式だけ。欄があるかどうかを検査すると、欄を埋めるためだけの文章が生まれる。入口でスロップを量産する可能性がある。
- 案: lint で検査するのは「書いてあるか」ではなく「検証できる形か」に絞る。
  - 完了条件が、テストかコマンドか計測値に対応しているか（mizchi の言う「数値で回せる指標」と同じ考え方）
  - 「壊れたらどこで分かるか」が書かれているか（2.5 とつながる）
  - 取り消せない操作（スキーマ変更、公開、削除）を含むかどうかの申告
- 内容が良いかどうかは lint では判定せず、人間の判断点で見る。
- 公式の裏付け（§7 A）: Claude Code のベストプラクティスは、役に立つ spec の条件として次の 3 つを挙げている。「関わるファイルとインターフェースを名指しする」「スコープ外を明記する」「最後に E2E の検証手順を置く」。いずれも形式で検査できるので、lint の項目の第一候補になる。
- 公式の注意: plan mode には手間がかかる。「diff を 1 文で説明できるなら plan を飛ばせ」と書かれている。dev-crew は規模に関係なく spec と plan を通しているので、入口を固める前に、小さい変更で入口そのものを飛ばす条件を決めるほうが先。

### 2.3 関与の強さ: リスクで自動的に分けるか、判断材料を AI が出すか

- 事実: `skills/review/risk-classifier.sh` のバックテスト（docs/research/risk-classifier-backtest.md）では、DB・認証を扱うプロジェクトで HIGH が過半数になった。リスクのスコアで経路を自動的に分けると、ほぼ全件が重い経路に入る。
- 提案（人間を判断の中心に置き、AI が背景・リスク・推奨方針を出して判断を速くする）の良い点: 判断を人間に残したまま速くできる。自動分類の精度に依存しない。
- 弱い点 1: 判断資料そのものが、AI スロップの発生源になりやすい。
- 弱い点 2: 推奨方針に人間が引っ張られる（アンカリング）。承認が形だけになり、人間が判断している外形だけが残る。
- 案: 判断資料（Decision Brief）の型を固定し、長さを予算で縛る。

```
決めること:        1 行
選択肢:            2〜3 個
推奨と理由:        1 つ。推奨しない選択肢を選ぶべき条件も書く
推奨が外れたときの損失: 取り消せるか / 誰が困るか
確認していないこと:  AI が置いた仮定の一覧
長さ:              1 画面以内（超えたら別紙にし、本文には要点だけ）
```

- スロップを抑える鍵は、説明ではなく証拠を載せること。公式は「成功を主張させず、証拠を見せさせよ」と書いている。証拠とは、テストの出力、実行したコマンドとその結果、スクリーンショットのこと。証拠を確かめるほうが、検証を自分でやり直すより速い。Decision Brief の本文は、文章で説明するより証拠へのリンクを並べる。
- 公式の方向も同じ（§7 E）。トレンドレポートは、人間の監督が「全部をレビューする」から「重要なものをレビューする」へ移ると予測している。エージェントは、判断が要る場面を自分で見分け、不確かな点を挙げ、事業に影響する決定を人間に上げる。これは「AI が判断材料を出し、人間が判断する」案に一致する。
- リスク分類の役割は「どの判断点を人間に出すか」を選ぶことに限定し、判断そのものは人間がする。
- project-ops:propose がすでに Decision Brief を出している。新しく作るより、この型を流用するほうが安い。

### 2.4 人間は判断を中心にする

- 同意する。dev-crew の CLAUDE.md にある「人間の判断点を 3 か所に置く」は、すでにこの方向を向いている。
- 弱い点: 判断だけを続けると、判断に必要な理解が育たない。他組織との対話で出た育成の問題（AI を使うと失敗しないので身につかない）と同じ根を持つ。
- dev-crew のスコープ外だが、判断点で出す資料（explainer）が、判断する人にとって唯一の学習の機会になっている、という見方はできる。
- 公式も、この問題に解決策は示していない。トレンドレポートには、Anthropic のエンジニアの言葉として「答えがどうあるべきか分かる場面で AI を使っている。その力は『苦労して』ソフトウェアを作って身につけた」とある。同じレポートによれば、エンジニアは仕事の約 60% で AI を使うが、完全に任せられるのは 0〜20% にとどまる。

### 2.5 計測ポイントを設計時に決める

- 事実: 性能の問題がレビューを通り抜け、本番のアラートで見つかっている。レビューの観点を増やすより、計測を前に寄せるほうが効く可能性が高い。
- 案: 修正のたびに、評価ポイントを 4 層で考える。

| 層 | 例 | いつ分かるか |
|---|---|---|
| コード | 静的解析、複雑度 | REVIEW |
| テスト | 修正前の実装で FAIL すること、mutation | REVIEW 前 |
| 実行時（CI） | ログ、slow query、EXPLAIN、ベンチマーク、メモリ | CI |
| 本番 | アラート、インシデント、revert | リリース後 |

- spec に「この変更が壊れたら、どの層で分かるか」を書かせる。答えが「本番でしか分からない」なら、その変更は CI での計測を足す候補になる。
- 良い点: 非機能の要件を、レビューする人の注意力に頼らずに捕まえられる。
- 弱い点:
  - dev-crew はプラグインで、本番インフラはプロジェクトごとに違う。dev-crew が持てるのは「どこで分かるかを問う」ところまで。計測の実装は導入先のプロジェクトがする。
  - 個人開発の導入先には、本番の計測がほとんど無いものもある。
  - 計測を増やしすぎると、アラート疲れが起きる。
- 本番の事象（revert、インシデント）を次のサイクルの入力に戻す経路は今は無い。cycle-retrospective の入力に足すのが最も安い。
- 公式の SDLC プレイブック（§7 D）は、指標を段階ごとに先行指標と遅行指標に分けて置いている。例として、初回で通る PR の割合、一次 CI の成功率、変更失敗率（DORA）、本番インシデントと回帰の推移がある。保守の段階では、異常を検知したら AI が診断し、次の intent を起こす。dev-crew が導入先に案内する指標のひな形として流用できる。

## 3. 統合したフロー（案）

```
入口   意図 + 背景
       spec lint: 完了条件が検証できる形か / 壊れたらどこで分かるか / 取り消せない操作を含むか
       質問は高コストの点だけ。他は仮定を置いて記録する
  |
過程   AI に任せる（テストを先に書く順序、フェーズの細分化は強制しない）
  |
出口   決定論のゲート: テストが修正前に FAIL する / テストの弱体化を検出する / CI で計測する
       多視点レビュー（Claude + Codex）
  |
判断   Decision Brief（型を固定し、1 画面以内）+ 仮定の一覧 -> 人間が OK / NG
  |
観測   本番のアラート / インシデント / revert -> retrospective -> 観点と計測を更新
```

## 4. dev-crew と周辺スキルへの反映候補

| 候補 | 今ある部品 | 変えること | 先に確かめること |
|---|---|---|---|
| 過程ゲートを出口ゲートに置き換える | `scripts/gates/pre-red-gate.sh`、`pre-commit-gate.sh` | 現行のゲートは「手順を踏んだか」（sync-plan、REVIEW の完了）を検査している。これを「出力が条件を満たすか」（修正前に FAIL する、テストが弱くなっていない）の検査に寄せる | 現行の過程ゲートが止めた件数と、止めたことで防げたもの |
| spec の入口 lint | spec スキル、`exspec-check.sh`（テストの静的解析） | 完了条件が検証できる形か、壊れたらどこで分かるかを検査する | lint が欄埋めの文章を生むかどうか（数サイクル試す） |
| 判断資料の型 | CLAUDE.md の判断点 3 か所、project-ops:propose | Decision Brief の型と長さの予算。yomiyasu と first-reader を最後の検査に置く | 人間が判断に要した時間、読まずに承認した回数 |
| 仮定を記録して事後に見せる | AskUserQuestion、Cycle doc | 質問を高コストの点に限る。仮定の一覧を Cycle doc と報告に載せる | 仮定のうち、人間が覆した割合 |
| 計測ポイントの設計 | observability-reviewer、performance-reviewer | spec に「どの層で分かるか」を入れる。CI 計測の雛形を onboard で案内する | 導入先に CI 計測を足す余地があるか |
| 本番の事象を戻す | cycle-retrospective、codify-insight | revert とインシデントを retrospective の入力にする | revert が実際にどれだけあるか（git log で測れる） |
| リスク分類の役割を変える | risk-classifier.sh | 経路を自動で分けるのではなく、人間に出す判断点を選ぶことに使う | バックテストの HIGH 過半数問題が、この用途でも効くかどうか |
| 小さい変更では入口を飛ばす（公式由来） | spec、plan mode | 「diff を 1 文で説明できる」変更は、spec と plan を経ずに実装し、出口ゲートだけを通す | 過去の Cycle のうち、1 文で説明できた変更の割合 |
| レビュー指摘を絞る（公式由来） | review、socrates、Codex competitive review | 正しさと要件に関わる指摘だけを必須にし、残りは任意にする。公式は、指摘を全部追うと過剰設計になると警告している | 過去の REVIEW 指摘のうち、正しさに関わったものの割合 |
| テストの改竄をフックで止める（公式由来） | `scripts/hooks/`、pre-commit-gate | 実装の段階ではテストファイルの編集を禁止する。SDLC プレイブックが推奨している | 出口ゲートの「テストの弱体化検出」と重複しないか |
| CLAUDE.md と rules を削る（公式由来） | CLAUDE.md、AGENTS.md、rules/、SKILL.md | 1 行ずつ「消したら Claude は間違えるか」を問う。指示なしでも正しく動くものは消すか hook にする | 削る前後で挙動が変わるかを観察する（公式の検証方法そのもの） |
| /goal と Stop hook を出口に使う（公式由来） | orchestrate | 完了条件を /goal か Stop hook で持たせ、終わったかどうかを、作業したモデルとは別のものに判定させる | /goal の評価者は会話しか読まない。条件をテスト出力のような形で書けるか |

## 5. 先にやる比較実験

上の候補はどれも推測で、裏付けがない。入れる前に、現行のフローと最小のフロー（CONSTITUTION + 出口ゲートだけ）を、同じタスク数件で比べる。

測るもの:

- 所要時間とトークン
- 人間の介入回数と、判断にかかった時間
- REVIEW の指摘数と、commit 後の revert / 手戻り
- 人間が報告を読み切れなかった回数（自己申告）

件数は少なくなるので、統計的な結論は出ない。方向が明らかに逆かどうかだけを見る。

やり方は Anthropic のハーネス記事（§7 B）にならう。構成要素を一度に 1 つずつ外し、そのたびに影響を測る。記事では、一度に大きく削った最初の試みは性能を再現できなかった。そこで 1 つずつ外したところ、モデルの世代が上がるにつれて次のように変わった。

- スプリント分割とコンテキストのリセットは不要になった。
- planner と evaluator は残った。planner が無いと、仕様が薄く、機能の少ないアプリしかできなかった。

### 実験の形（2026-10-14 追記）

**稼働中のプロジェクトのコピー上で、過去の変更を再演する。** 稼働中のリポジトリには触れない。

- 過去の Cycle を選び、変更前の commit から、当時の spec をもとに 2 つの条件で `claude -p` を実行する。
- 条件は、現行フローと最小フローの 2 つ。
- 正解の基準には、実際にマージされた commit のテストを使う。AI には見せない。

**対象のプロジェクト**

| 位置づけ | プロジェクト | 理由 |
|---|---|---|
| 主対象 | 大規模の Python プロジェクト | Cycle とテストが多い。変更が PR 単位で切れていて、Opus 5.5 世代の履歴が多い |
| 小規模の対照 | 小規模の Python プロジェクト | Cycle はすべて完了済みで、テストが短時間で通る |
| 高リスク領域（任意） | 認証と決済を持つ TypeScript プロジェクト | ただしテストに DB が要る |

対象外: 業務委託先や顧客のプロジェクト。

**`claude plugin eval` は主な枠組みには使わない。** 理由は 3 つ。

- 実行のたびに空の workspace から始まり、既存のリポジトリを指定する仕組みが文書に無い。
- 比較できるのは「プラグインあり / なし」だけで、プラグイン A 対 B の比較機能が無い。
- プロジェクトの CLAUDE.md、AGENTS.md、`.claude/rules` を読み込まない。

一方で、回数を決めた繰り返し実行と、手順の検査（`tool_used`、`tool_order`）には使える。フローの見直し後に、フェーズ単位でスキルの回帰を検出する用途に回す。

dev-crew で外す順番の候補は、効果が小さく手間が大きいものからにする。

1. 小さい変更での spec / plan
2. 過程ゲート（pre-red-gate）
3. フェーズの細分化
4. レビュアーの人数

## 6. 未決事項

- §3 の前提を書き換えるなら、CONSTITUTION §8 により ADR が要る。実験の後に起こす。
- 個人開発（dev-crew の主な導入先）と組織開発で、フローを分けるか。「思想は 1 つ、運用の強さに幅を持たせる」で足りるかどうか。
- Non-Goal「最小トークン消費」を維持するか。組織に導入するとコストが主要な論点になる。
- 入口 lint と Decision Brief の両方が、新しいスロップの発生源にならないか。両方とも長さの予算を持たせるのが前提。

## 5.5 パイロットの結果（2026-10-14、1 件 × 2 条件 × 1 回）

主目的は、測定の道具が使えるか確かめること。件数が 1 件なので、仮説の判定には使わない。

**ケース**: 大規模 Python プロジェクトの過去の不具合修正（小規模）。パーサの空セルで例外が出て、その日の取り込みが全滅する、というもの。AI に渡したのは Cycle doc の「背景 / 問題」の節だけ。原因と解法は渡していない。

**条件**:

- A: プロジェクトの CLAUDE.md / AGENTS.md / rules + dev-crew 2.18.2
- B: 手順の記述を外し、事実だけを残した AGENTS.md。プラグインなし。「完了前にテストを実行して結果を示せ」とだけ指示した

**注意: A は現行フローの全体ではない。** A が実際に走らせたのは /orchestrate 以降（設計レビュー → RED → GREEN → REFACTOR → REVIEW → retrospective → codify → commit）だけ。spec スキル、plan mode、sync-plan、architect、人間の承認は 1 度も通っていない。したがって、

- 比較は「orchestrate 以降 対 最小」であり、「現行フロー 対 最小」ではない。
- 時間とコストの倍率は、現行フロー全体の倍率ではない。spec の工程と人間の承認時間が入っていない。
- H5（spec / plan の有無の効果）について、このパイロットは何も言えない。どちらの条件も spec を通っていない。
- ゲートの発火: pre-commit-gate は実行されて PASS した。pre-red-gate はログに痕跡がない。sync-plan を経ずに RED に進んでいるので、headless でゲートが効いていたかは未確認。原則 6（決定論的プロセス保証）が headless で成り立つかどうかは、本番の実験で確かめる。

両方とも `--setting-sources project` でユーザー設定を外し、Opus 5.5、auto モードで実行した。

## 5.6 本番の設計（2026-10-14、結果を見る前に記録）

**ケース**: パイロットと同じ大規模 Python プロジェクトの過去の変更 5 件。規模は「テストと docs を除いた差分」で分けた。

| 規模 | 内容 | 実際の修正（テスト以外） |
|---|---|---|
| 小 | 取り込み処理が、パーサの計算済みの値を捨てていた | 1 ファイル 5 行 |
| 小 | 正規化処理の連鎖削除が、古いレコードの生データを全消しする | 1 ファイル 12 行 |
| 中 | 予測時の欠損特徴量を、学習時と同じ扱いにそろえる | 2 ファイル 29 行 |
| 中 | 取りこぼしを埋める処理の対象範囲が狭すぎる | 1 ファイル 35 行 |
| 大 | 日次パイプラインに正規化の段を足し、バックフィル用のサブコマンドを作る | 4 ファイル 272 行 |

候補 7 件から 5 件を選んだ。外した 2 件のうち、中の 1 件は別の中のケースと同じテストファイルを触るので外した。大の 1 件は、隠したテストが新しいモジュールとクラスの名前を前提にしていて、仕様として公平に渡せないので外した。そのため大は 1 件だけで、H5 の大側は 1 点しかない。

**隠したテストの前提を確かめた**: 各ケースで、(a) 修正前のコード + 隠したテスト → 一部 FAIL、(b) 修正前のコード + 実際の修正 + 隠したテスト → 全 PASS、を実測した。最初は (b) で 11 件落ちた。原因はコピーに `data/` ディレクトリが無いことで、作業ディレクトリと同じ状態にそろえて解消した。

**インターフェースの扱い**: 隠したテストが関数名や CLI 引数を名指しするケース（中の 1 件、大の 1 件）では、外から確認するインターフェース（関数名、サブコマンド名、窓の上限など）を受け入れ条件として task に書いた。両条件に同じ task を渡すので公平で、実際のフローでも plan に書かれる内容。ほかの 3 件は「背景 / 問題」の節だけを渡した。

**A の入口を通す方法**: パイロットでは、A がプロンプトの指示で spec と plan mode を飛ばした。本番では構造で通す。

1. 段階 1: `--permission-mode plan` で起動し、/dev-crew:spec から plan review（Step 8）まで進める。headless では ExitPlanMode が使えない（試走で確認）ので、計画ファイルを書いたところで止まる。
2. 段階 2: 同じセッションを `--resume` し、auto モードで「計画は承認された。/dev-crew:orchestrate で commit まで」と渡す。
3. 時間・コスト・トークンは 2 段階の合計で数える。

人間の承認は自動承認で代用している。承認にかかる人間の時間と、承認で計画が変わる効果は測らない（§6.5「決められないこと」）。

**その他の条件**:

- A: spec の Version Gate がプロジェクトに記録された版と導入版の一致を見るので、onboard 済みの状態にそろえた（版の記録だけを更新）。段階 1 では codex / bash / jq の Bash 実行を許可した（普段の対話セッションでは許可している操作）。
- 実行も採点も 1 件ずつ順番に行う。並行で走らせると、時間に依存するテストが不安定になり、AI がそれを追いかけて結果が汚れるおそれがあるため。
- 1 ケースにつき各条件 2 回。1 周目を全ケース流してから 2 周目を流す。

## 6.5 仮説と判断基準（2026-10-14、実験前に固定）

結果を見る前に書く。結果を見てから基準を変えない。

### 価値判断（CONSTITUTION から導く）

| 問い | 判断 | 根拠 |
|---|---|---|
| 何を最適化するか | 壊れにくさを下げないことを制約にし、そのうえで人間の判断負荷と速度を良くする | §2 Goal「人間の判断負荷を減らしつつ、壊れにくい変更を高速に出す」 |

| 個人向けか組織向けか | 主な対象は個人開発（人間 1 人 + AI）。組織とは思想を共有するところまで | §1「人間が楽をするための開発体制」。CONSTITUTION は組織の運用（承認の階層、チーム間の受け渡し）を扱っていない |
| 人間を外すか | 外さない。判断点は残し、判断を軽くする | §2 Non-Goal「人間排除、完全自動化」 |

### 予想（AI 開発の今後）

- モデルの世代が上がるほど、「過程の指示」（作業の順序、フェーズ分割、手順を踏んだかを見るゲート）の価値は下がる。反対に、「出口の検査」（隠したテストでの合否、テストの弱体化検出、計測）と「判断の受け渡し」（証拠、仮定の一覧、Decision Brief）の価値は上がる。
- そこから、dev-crew は「TDD のワークフロー」から、「検証と判断のハーネス + 世代ごとに測り直す仕組み」へ移る。TDD は手順としては残らない。テストを正解の基準として守る部分（修正前に FAIL する、テストを改竄しない）だけが残る。
- この予想が外れる条件: 最小フローが、隠したテストで繰り返し落ちる。かつ、その原因が出口の検査不足ではなく過程の欠如にある（例: テストを先に書かなかったために設計がずれた）。

### 仮説と、結果ごとの行き先

| # | 仮説 | 測るもの | 成立したら | 不成立なら |
|---|---|---|---|---|
| H1 | 最小フロー（B）でも、隠したテストの合格率は現行（A）と同等 | 隠したテストの合格件数 | 過程を削る方向に進む（§4 の「緩める」候補を実装する） | 部品を 1 つずつ A に戻し、効いている工程を特定する |
| H2 | B は A に比べて、壁時計の時間とトークンが半分以下 | 時間、トークン、ターン数 | H1 と合わせて成立すれば、削る優先度を上げる | 差が小さければ、削る価値は手間の分だけになる。優先度を下げる |
| H3 | B が落ちるとしたら、原因は出口の検査不足（テストを書かない、空振りのテスト、テストの書き換え） | B の失敗ケースで、修正前に FAIL するテストがあったか | 出口ゲートを先に固め、それから過程を削る | 過程に効いている部分がある。H1 の「不成立なら」と同じ扱い |
| H4 | A のレビュー指摘のうち、正しさや要件に関わるものは少数 | REVIEW の指摘を分類した数 | レビューを「正しさのみ必須」に絞る | 多視点レビューを維持する |
| H5 | 小さい変更では、spec / plan の有無で結果が変わらない。大きい変更では変わる | ケースを規模別に分けたときの H1 | 規模で入口を分ける（小さい変更は入口を飛ばす） | 入口を全件に残す |

判定の目安: 件数が少ないので、統計的な有意性は求めない。2 回の実行の両方で同じ向きに差が出たら「差あり」とする。片方だけなら「差なし」とする。

### この実験で決められないこと

- 人間の判断点の効果。再演では止めずに自動承認しているため、測れない。判断点については、別途、実運用で介入記録を取る（HITL/HOTL 案 D）。
- ゴールを 1 回渡してループさせる形のように、タスクの形そのものを変える方向。再演の入力は過去の spec なので、今のやり方の枠の中での比較になる。
- 長期の保守性（読みやすさ、変更のしやすさ）。隠したテストは機能の正しさしか見ない。

## 7. Anthropic 公式情報の調査（2026-10-14）

### A. Claude Code ベストプラクティス（公式ドキュメント）

- 検証が中心にある。「Give Claude a check it can run」。検証が無ければ「終わったように見える」が唯一の信号になり、人間が検証のループを担うことになる。
- 検証の固さは 4 段階ある。後の段階ほど準備の手間が増え、人間の注意が減る（「Each step trades setup for attention」）。
  1. プロンプトで頼む
  2. `/goal` の完了条件にする（作業したモデルとは別の評価者がターンごとに判定する）
  3. Stop hook で決定論的に止める
  4. 新しいコンテキストの subagent に反証させる
- 成功を主張させず、証拠を見せさせる。テストの出力、実行したコマンドと結果、スクリーンショットなど。
- plan mode には手間がかかる。「If you could describe the diff in one sentence, skip the plan.」
- 大きい機能では、AskUserQuestion で人間にインタビューさせて SPEC.md を書かせ、実装は新しいセッションでやる。役に立つ spec は、ファイルとインターフェースを名指しし、スコープ外を明記し、最後に E2E の検証手順を置く。「spec を正確にする時間は、実装を見守る時間より割に合う」。
- CLAUDE.md は短く保つ。1 行ずつ「Would removing this cause Claude to make mistakes?」と問う。長すぎると、肝心のルールが埋もれて無視される。指示なしでも正しく動くものは、消すか hook にする。変更したら、挙動が実際に変わるかを観察して確かめる。
- 指示（CLAUDE.md）は助言にすぎない。hook は決定論的で、必ず実行される。
- 敵対的レビューには注意がある。「gaps を探せ」と頼まれたレビュアーは、作業が健全でも何かしら報告する。それを全部追うと過剰設計になる（抽象化の層、防御的なコード、起こりえないケースのテスト）。正しさと要件に関わる指摘だけを求める。
- 結びは「These patterns aren't set in stone」。何が効いたかを観察して、直感を育てるよう勧めている。

### B. Harness design for long-running application development（Anthropic Engineering、2026-03-24）

- エージェントは自分の成果物を甘く評価する。作業者と評価者を分けるのが強いレバーになる。独立した評価者を懐疑的に調整するほうが、生成者に自己批判させるより扱いやすい。
- 評価者にも限界がある。問題を見つけても「大したことはない」と自分で納得して承認してしまう。テストが表面的になる。
- 世代が上がるたびに、ハーネスを 1 部品ずつ外して測った。Opus 4.5 でコンテキストのリセットが不要になり、Opus 4.6 でスプリント分割が不要になった。評価者はスプリントごとではなく、最後に 1 回だけ走らせる形になった。planner と evaluator は残った。
- 評価者を入れる価値は固定ではない。「worth the cost when the task sits beyond what the current model does reliably solo」。
- コストの例: 単独で 20 分 $9 だったものが、フルハーネスでは 6 時間 $200 になった。
- 限界: 著者による少数の実験で、統計的な比較はない。

### C. Loop engineering: Getting started with loops（Claude Code チーム、2026-06-30）と /goal の仕様

- ループは 4 種類ある。ターン単位、ゴール単位（`/goal`）、時間単位（`/loop`、`/schedule`）、イベント駆動。まず最も単純なものから始める。
- 完了条件には、決定論的な基準（通ったテストの数など）と、ターン数の上限を入れる。同じ問題が繰り返し起きたら、個別に直すのではなく、仕組みに組み込む。
- `/goal` の評価者は small fast model で、会話しか読まない。コマンドを実行することも、ファイルを読むこともしない。そのため、条件は Claude 自身の出力で示せる形に書く。条件に書くとよいものは 3 つ。
  - 測れる 1 つの終了状態
  - それをどう証明するか
  - 途中で変えてはいけないもの（例: 「他のテストファイルは変更しない」）
- `/goal` は prompt ベースの Stop hook を包んだものなので、判定はモデルによる。決定論的な判定が欲しいなら、スクリプトの Stop hook を使う。

### D. The AI-native SDLC playbook（claude.com、2026-08-21）

- 「Code is no longer the bottleneck」。ボトルネックは、計画、レビューとテスト、デプロイという、人間の速度で動く工程に移った。
- 各段階で、次の段階が読める成果物を残す（intent.md、spec.md、plan.md、PR、インシデントの記録）。これがそのまま監査の証跡になる。「spec と TDD は説明責任として残る」という見立てと一致する。
- 承認はリスクで振り分ける。ルーチンの変更はエンジニアが承認し、高リスクの変更はリードに回す。規制対象のコードは人間のレビューを維持する。「The agent does everything up to the production gate and nothing past it.」
- バグ修正では、先に失敗するテストを書く。テストファイルの編集は hook で禁止する。TDD という言葉は使っていないが、テストを正解の基準として守る部分は残している。
- 統制はコード（hook、managed settings）で強制する。「Human judgement stays above it.」

### E. 2026 Agentic Coding Trends Report（Anthropic）

- エンジニアは仕事の約 60% で AI を使うが、完全に任せられるのは 0〜20%。
- 人間の監督は「全部をレビューする」から「重要なものをレビューする」へ移る。エージェントは、助けが要る場面を見分け、不確かな点を挙げ、事業に影響する決定を人間に上げるようになる。
- 任されやすいのは、検証しやすい作業と、失敗しても損が小さい作業。設計に依存する作業と概念的に難しい作業は、人間の手元に残りやすい。
